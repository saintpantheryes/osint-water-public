# 系统计划:水务项目机会持续追踪

> 2026-09-24 重新对齐。此前两次会话把"阿塞拜疆试点"做成了人工调研,系统本体停在 P0 一半;本文件把系统目标、架构、分工和阶段写死,之后的工作以此为准。

## 目标

像舆情监控系统一样**持续追踪**多个国别的水务项目机会:信源定时采集 → 发现新公告与变动 → 判定相关性、抽取关键字段 → 挂到项目台账 → 在系统内提醒 → 定期自动出报告。分析单位是国别,报告以项目为粒度;加国别只改配置,不改代码。

衡量标准:公告发布后**一天内**出现在系统提醒里。反例是本次人工调研:苏姆盖特污水厂咨询意向书 2026-08-24 挂在国家水资源局网站上、09-16 截止,人工 09-24 才发现。

|---|---|

## 已定事项(2026-09-26)

使用方看过阿塞拜疆成稿后提出三项要求:① 像舆情监控一样跟踪各网站的水务项目机会,可按水利、供水、污水等领域分类,也可按大洲、国别分类,并能自定义筛选;② 可以筛选信息来源网站,支持用户提交网址或信息检索入库;③ 能做分析,按报告模板输出 Word 报告。

| 事项 | 决定 |
|---|---|
| 使用形态 | 网页系统,先在本机运行(Mac 双击 `start_mac.command`),以后可原样部署到服务器;每天的采集仍由 GitHub Actions 完成。界面打开时从私有 `data` 分支拉取,界面上的改动推回 `data` 分支;界面写的文件(处理标记、保存的筛选、用户信源、人工提交的线索)与定时任务写的文件分开,互不覆盖 |

| 信源 | 在国别信源之外加全球信源(`global/watch.yaml`:世行采购公告、EBRD、伊斯兰开发银行、欧佩克基金、美洲开发银行、亚投行公告与项目库、联合国开发署;另有摩洛哥公共采购门户,沙特 Sharakat、阿曼 Nama PWP 的水务 PPP 新闻栏),复测记录见 `docs/sources/D1_2026-09-26_复核.md`;用户可在界面上停用内置信源、添加网站(先试抓取再保存)。原国别配置里的 EBRD、世行采购、欧佩克基金、IsDB 由全球信源接替,沿用其已见记录 |

## 架构

```
信源登记(countries/{ISO3}/watch.yaml + global/watch.yaml + 用户在界面上添加的网站;各类采集器)
  → 定时采集(如实 UA、限速、403/429 即停)
  → 去重与变更检测(新公告 / 页面变化)
  → 规则初筛(多语种水务词 × 领域 × 机会阶段词;定国别)
  → 大模型判定与抽取(是否相关、类别、领域、国别、截止日、金额、出资方、资格限制、原文依据、中文摘要、对应台账项目)
  → 线索库(signals,自动,量大;另有人工提交的线索)
  → 提醒(新机会、截止临近、建议更新台账、过期节点、信源故障)
  → 周报 / 月度国别报告 / 按成稿版式的国别报告、领域专题、线索简报(Markdown + Word)
  → 本机网页界面(热榜、监测与筛选、处理标记、商机与操作记录、待确认、搜索入库、分析、预警、报告、流程导览、信源管理)
```

三层数据,分工清楚:

| 层 | 内容 | 谁写 |
|---|---|---|
| 线索(signals) | 采到的每条公告、新闻、页面变动,带规则与模型判定结果 | 系统自动 |
| 台账(ledger) | 已确认的项目机会,每条事实带来源 | 人确认(系统给建议) |
| 提醒与报告 | 由线索和台账派生 | 系统自动 |

原计划"不做跨源自动合并"的原则调整为**可靠的自动写、其余机器建议人工确认**(2026-09-27,使用方要求台账默认自动更新、只加提醒):
挂接可靠(编号吻合,或模型读原文后确认、把握高)且模型判为相关的线索,定时任务在监测之后自动写进台账——登记来源(核实方式标
"系统自动写入,未经人工核对")、新增或加引用节点与标段、前期项目出了采购公告改为"采购进行中",每条线索一次提交;写了什么记在
`data` 分支 `watch/ledger_auto.jsonl`,界面「待确认」页提醒过目,"撤销"按内容删掉那次写入的(别的来源也引用了的留着)。
只按名称或模型判断、把握不大的挂接,以及可能的新商机,仍由人决定(「待确认」页):"并入并更新台账""建成商机"按线索预填,人打开原文核对后逐项确认,
写入前整体校验,写入后提交到 main 分支(每次保存一个提交,可追溯、可还原);不是的可成批标为"都不是""不是商机",已过截止日的默认收起。
新商机入账的口径是**跟踪即入账**:线索设了跟踪进展、还没并入商机、没有可靠(●)挂接也没写进过台账时,系统按线索建商机(在台账里新建项目,
所在国还没有台账的连台账一起建;core/ledger_auto.py 的 enter_ledger,界面与表格拉回共用);已处理或忽略(没设进展)的不列为可能的新商机。
截止日这类提醒直接从一手来源生成。

**商机**(2026-09-30,使用方的流程图「线索 → 判定 → 商机 → 报告」,国别基础信息另入报告):一个项目一条商机,沿用台账编号;公开事实在台账里,
进展、优先级、负责人、所属线索与操作记录挂在商机上(core/opportunity.py)。一条线索至多属于一个商机:人的决定(member 事件)> 写进台账的
(界面更新、自动写入、原文网址已是来源)> 编号吻合或模型确认且只挂上一个的自动并入;其余进「待确认」。商机的进展取商机与所属线索上最近设的一次。
AI 推荐、人确认:可能的新商机由管理员在「待确认」里建成商机。后续步骤(待使用方看过前两步再定):团队表格「项目台账」改为商机表、
「跟踪进展」从线索表移到商机表;台账来源补登为线索(内部与 D 级来源除外);报告加商机进展、有商机的国别出周期报告。

私有 `data` 分支(孤立分支,不带 main 的历史;工作流检出到 `data/private`,即私有 profile 的 `data_dir`;公开前删除,见 `docs/PUBLISHING.md`):

```

inbox/{ISO3}.md              分国提醒页(每次运行覆盖)
inbox/GLOBAL.md              其他国别的线索(全球信源,按大洲分组)
watch/state.json             各信源的已见条目、内容指纹、最近运行与健康状态
watch/signals/YYYY-MM.jsonl  线索(一行一条;补判模型结果时原行替换)

watch/summary.json           同一份摘要的数字:新增相关线索、14 天内截止、信源异常,自动入账后补上条数(表格「每日摘要」用)

watch/events.jsonl           操作记录:处理标记、跟踪进展、备注、台账核对,带时间与操作人 by(本机岗位代号 / system;只追加,几处同时追加都保留)
watch/ledger_auto.jsonl      台账自动写入记录(定时任务写,只追加;对账补记的标"记录缺失")
watch/teable_state.jsonl     表格(Teable)各条记录每次同步时的人管字段值与对应的系统值(只追加,同一记录取最新一行;拉回据此判断同事改了什么,推送据此把本机改了、表格没改的写回;已拉回的跟进记录;最近一次拉回的冲突)
watch/teable_links.json      表格的网址、库与表的 ID、各条线索与项目的记录 ID(推送时写;本机界面"在表格里打开"用)
watch/submitted/{id}.json    人工提交的线索(一条一个文件,界面写入;定时任务只补判模型结果)
watch/views.yaml             界面上保存的筛选
watch/sources_user.yaml      界面上添加的网站、停用的内置信源
reports/weekly/              周报(Markdown + Word)
reports/monthly/             月度国别报告、国别动态报告与线索简报(Markdown + Word)
reports/custom/              界面上生成的报告
snapshots/、run_log.jsonl     宏观指标与台账快照
```
